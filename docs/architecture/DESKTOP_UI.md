# Desktop UI system

VantaOS uses a kernel-owned software compositor with a persistent shadow framebuffer and 16×16 damage tracking. It is not yet a VSync/page-flip compositor. Because it does not yet have a general widget toolkit, rendering helpers and input hitboxes remain an application-level contract: visual changes must update matching input geometry in the same change.

## Visual rules

- Use semantic colors from `include/desktop_theme.h` for shared surfaces, text, borders, and accents.
- Use `graphics_draw_window_frame` for application window chrome. Apps that expose minimize/maximize/close controls must pass `show_window_controls = 1` and keep those hitboxes aligned with the rendered 46-pixel titlebar. Apps without those behaviors pass `0` and render only Close.
- Prefer a quiet desktop background, a small number of useful shortcuts, and one restrained accent. Decorative status indicators are not allowed unless they report real state and have a defined action.
- Group related controls with spacing and alignment before adding extra borders. Keep labels short and consistent; reserve high-contrast accent colors for selection and actionable state.
- Terminal output must remain readable at the framebuffer's current fixed bitmap-font size. The visible-line calculation and cursor position must use the same line-height value.

These rules follow the general principles in [Microsoft Fluent 2 layout guidance](https://fluent2.microsoft.design/layout), [Fluent 2 accessibility guidance](https://fluent2.microsoft.design/accessibility), and [Nielsen Norman Group's usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/): consistent spacing and hierarchy, adequate contrast, predictable controls, and visible system state.

## Rendering and input ownership

- `kernel/graphics/graphics_ui.c` owns shared desktop chrome and the software-rendered desktop surface.
- `kernel/graphics/graphics_input.c` owns pointer hit-testing for desktop shortcuts and global window controls.
- `os/desktop/file_explorer.c` owns Explorer navigation and list rendering.
- `os/desktop/desktop.c` owns Terminal window composition, while `os/terminal/terminal.c` owns terminal history and cursor state.
- `include/desktop_theme.h` defines shared semantic color tokens.

The current implementation is a software compositor, not a GPU compositor or widget toolkit. All ordinary window drawing should go through the shadow buffer and damage tracker; do not add scanout-direct fast paths for cursor or window updates. Keep drawing and hitbox changes paired, and validate the result by inspecting the screenshot generated by the QEMU workflow. See [compositor and display presentation](COMPOSITOR.md) for VSync and NVX limits.

## Process model status

The desktop, Terminal, and Files currently have kernel process-table entries. That is not the same as running each app as a protected ring-3 user process: the GUI is still rendered and hit-tested by kernel-side code, and the Files process is currently a persistent kernel-side lifecycle placeholder. The user-mode ELF loader and syscall ABI exist, but a proper user-space GUI application model still needs a window-server/event IPC contract before moving these apps out of the kernel. Do not describe these GUI apps as isolated user-mode programs until that work is implemented and tested.


## Desktop composition refresh

The desktop layout is composed by `kernel/graphics/graphics_ui_detail.c` into the compositor's shadow surface. This is a native framebuffer layout layer, not a userspace toolkit. The renderer uses opaque fills and integer geometry; blur, alpha transparency, GPU acceleration, and atomic page flips are not available and must not be implied by the UI.

### Visual hierarchy

- **Workspace identity:** the topbar names the current workspace and reports only the VFS readiness state exposed by the kernel.
- **Launch surface:** the three desktop shortcuts retain their hitboxes in `graphics_input.c`. The Start menu pins Terminal, Files, System, and Settings; each row uses the same geometry as its click dispatcher. The physical left or right Super/GUI key toggles the Start menu, as does the taskbar Vanta mark.
- **Overview:** architecture, VFS initialization, and process-manager initialization are shown as separate status cards. These cards must remain grounded in existing APIs; do not add fabricated memory, CPU, network, uptime, or battery numbers.
- **Application pages:** System and Settings share the same surfaces, typography, divider treatment, and spacing. Resolution controls must keep the exact geometry used by the input handler.
- **Explorer:** navigation, column headers, selection rows, empty state, and status footer use the shared component layer. The footer reports the number of directory entries returned by the VFS and labels the source as VFS; it does not claim persistent-disk capacity or file timestamps.
- **Terminal:** titlebar, session strip, output surface, and status strip are separate visual regions. Scrollback state comes from the terminal history API.

### Geometry contract

The current UI is drawn with a fixed-size bitmap font. Layouts must account for that rather than using web/CSS assumptions about font metrics. Every new clickable control requires an explicit input-handler update in the same change. Decorative cards must not look like buttons unless their action exists.

When a layout is rendered at multiple framebuffer sizes, content must be clipped or omitted deliberately. In particular, Explorer reduces the number of visible rows to keep its status footer from covering entries. Dashboard cards are omitted at small resolutions rather than rendered into overlapping columns.
