# RTL8188EU PHY profile format

The binary profile format and validator below are retained for future board-specific overrides and regression testing. Normal bring-up now uses the embedded, attributed RTL8188E reference MAC/baseband/AGC/RF tables and does not require `/SYSTEM/RTL8188EU.PHY`. The reference sequence then applies eFuse-derived TX power, crystal/LC calibration, and bounded two-run IQ calibration. It remains experimental until CI and physical-adapter tests pass.

An optional profile can still be generated by a system integrator using `RTL8188EU_PHY_PROFILE=/path/to/profile.bin`; it is separate from `RTL8188EU_FIRMWARE`, which supplies `/SYSTEM/RTL8188EU.BIN`. The current embedded baseline path does not load this optional profile.

## Binary format (little-endian)

The 24-byte header is:

| Offset | Size | Meaning |
| ---: | ---: | --- |
| 0 | 8 | ASCII `V8EUPHY1` |
| 8 | 2 | Format version, currently 1 |
| 10 | 2 | Header size, 24 |
| 12 | 4 | Total file size, including header |
| 16 | 4 | CRC-32/IEEE of all record bytes |
| 20 | 1 | Exact RTL8188E chip cut; wildcard `0xff` is rejected |
| 21 | 1 | Reserved, must be zero |
| 22 | 2 | Record count |

Each record is 16 bytes:

| Offset | Size | Meaning |
| ---: | ---: | --- |
| 0 | 1 | Operation code |
| 1 | 1 | Initialization phase |
| 2 | 1 | Reserved, zero |
| 3 | 1 | Reserved, zero |
| 4 | 2 | Register address |
| 6 | 2 | Reserved, zero |
| 8 | 4 | Register mask |
| 12 | 4 | Value / expected value |

The record array must exactly fill the declared file size. The loader checks the magic, version, lengths, exact chip cut, reserved bytes, CRC, operation/address ranges, masks, and phase ordering before it starts writing registers. Wildcard-cut profiles are rejected because RF and calibration values must not be applied to an unidentified silicon cut. Writes are read back and checked. Polls are bounded to 512 reads; delay operations require the kernel tick source and are capped at 100 ticks.

## Operations

| Code | Operation | Address space |
| ---: | --- | --- |
| 1 | Write 8-bit MAC register | address below `0x800` |
| 2 | Write 16-bit MAC register | address below `0x800` |
| 3 | Write 32-bit MAC register | address below `0x800` |
| 4 | Write 32-bit baseband register | `0x800–0x0fff` |
| 5 | Write 20-bit RF path-A register | RF address `0x00–0xff` |
| 6–10 | Poll corresponding MAC/BB/RF register | Same range as matching write |
| 11 | Delay by kernel ticks | address and mask must be zero; value 1–100 |

For writes, a zero mask means the full register width; otherwise the driver performs a masked read-modify-write and verifies the selected bits. Polls require a nonzero mask and succeed only when all masked bits match the expected value.

## eFuse-derived transmit-power data

The driver decodes all six RTL8188E CCK base indices (logical eFuse offsets
0x10–0x15), all five HT40 base indices (0x16–0x1a), and the packed signed
OFDM/HT20 deltas (0x1b). CCK groups cover channels 1–2, 3–5, 6–8, 9–11,
12–13, and 14; HT40 has five groups, with channel 14 excluded by policy.
Missing (`0xff`) or out-of-range base indices used by channels 1–13 are
rejected rather than replaced with guessed values. The unused channel-14 CCK
group may remain blank while channel 14 is disabled by policy. The driver derives channel-specific 1T legacy-rate and
MCS0–7 indices, programs the corresponding TXAGC baseband registers, and
checks readback. It reapplies power values for each selected channel.

Because the programmed MCS table currently targets 20-MHz operation, the embedded reference RF table configures the 20-MHz mode before TX-power programming. The optional profile validator also requires this setting in any future board-specific profile. This is not proof of calibrated RF output.

## Required phases

Records must be grouped in nondecreasing phase order:

1. MAC register setup
2. Baseband setup
3. AGC setup
4. eFuse-derived, board-specific TX-power programming
5. IQ calibration sequence and completion/result polls

Phases 1–4 must each contain at least one write. Phase 5 must contain at least one write and one poll. After phases 1–4 pass, the driver applies the factory crystal trim, requests LC calibration with bounded completion polling, restores the prior RF channel/bandwidth state, and only then executes phase 5. The software TX gate opens only after the entire profile and calibration sequence succeeds.

## Safety and validation limits

- CRC-32 detects accidental corruption; it is **not** a signature or authenticity check. Only use a profile obtained from a trusted source and validated for the exact adapter board and silicon cut.
- This format is an execution mechanism, not a source of calibration values. Do not fill it with guessed register values or a profile for a different board.
- A syntactically valid profile can still be electrically or functionally wrong. Host CI cannot establish safe RF power, correct calibration, actual scanning, association, WPA2 traffic, or Internet connectivity.
- No external profile is bundled or required for the built-in baseline. End-to-end RTL8188EU support remains unproven until physical-adapter tests pass.


## Built-in reference initialization

The driver includes MAC, baseband, AGC and RF initialization tables derived from FreeBSD's permissively licensed RTL8188E `r88e_priv.h`; attribution and the permission notice are retained in `rtl8188eu_phy_tables.h`. The baseline sequence applies these tables before eFuse-derived transmit power and crystal/LC calibration, so a generated `RTL8188EU.PHY` file is no longer required for baseline bring-up. This reference port is not proof of physical-device validation. Firmware compatibility, silicon-cut variants, RF timing/readback, IQ calibration, scan/receive behavior and real AP/WPA2/DHCP/DNS/HTTP interoperability still require CI and hardware validation. Transmission must remain disabled when any required stage fails.
